How Synchronizer Tokens Prevent CSRF

The Synchronizer Token Pattern works by generating a cryptographically random, unpredictable token (secrets.token_hex(16)) tied to the user's active session.

Verification Process:
  1. The server sends the secret token inside genuine HTML forms as a hidden input.
  2. Upon submission, the server verifies: request.form['csrf_token'] == session['csrf_token'].
  3. An external attacker's website cannot read this token from the victim's session due to the browser's Same-Origin Policy (SOP).
  4. Forged requests lack the token and are rejected with 403 Forbidden.

Table 2(e) Other Mitigations (Theory Alternatives)
  • Anti-CSRF Synchronizer Tokens (Implemented): Enforces presence of unique, unpredictable tokens on state-changing requests.
  • SameSite Cookie Attribute: Setting SameSite=Strict prevents the browser from sending cookies on any cross-site request, eliminating CSRF for modern browsers.
  • Re-Authentication for Sensitive Actions: Forcing password re-entry or two-factor prompts before altering email or passwords.
  • Custom Request Headers: Requiring custom headers (e.g. X-Requested-With) in AJAX requests, which cannot be forged cross-origin without CORS permission.
  • Avoid State-Changing GET Requests: Strictly ensuring GET requests are idempotent and non-mutating.
