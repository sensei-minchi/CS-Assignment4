What the database receives

The payload rewrites the query

SELECT * FROM users WHERE username = 'admin' -- ← comment starts here
' AND password = 'anything'
Everything after -- is ignored. The query the database actually runs is just:
SELECT * FROM users WHERE username = 'admin'
The password check is gone.

07 / 10
Root cause

Why it works

The input was allowed to change the structure of the query, not just its values.

Because the username is concatenated into the SQL text, a quote and a comment turn a two-condition check into a one-condition lookup. The database cannot tell the attacker's SQL apart from the developer's.

08 / 10
The mitigation

Parameterised query

 app.py — login() · the fix (diff)- query = "... username = '" + username + "' AND password = '" + password + "'"- row = db.execute(query).fetchone()
+ query = "SELECT * FROM users WHERE username = ? AND password = ?"+ row = db.execute(query, (username, password)).fetchone()

The ? placeholders keep the query fixed. The inputs are sent to the database separately, as data — they can never become SQL.

Defence in depth

One fix implemented, three more in theory

  • ✓
    Parameterised queries — implemented. Input can never alter query structure. The primary, most reliable fix.
  • ○
    Allow-list input validation Reject usernames containing ' -- ; before they reach the query.
  • ○
    Least-privilege DB account The app's account can only read users — limits the blast radius.
  • ○
    Safe error messages Never leak SQL or table names that help an attacker craft payloads.
